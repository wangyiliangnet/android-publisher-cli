# 架构说明

修改执行、状态或恢复逻辑前，先按本页的发布顺序找到对应模块。`release` 在本机保存发布内容、操作日志和渠道回执，并根据这些记录决定能否继续。操作者的命令步骤见[日常发布](daily-cli-workflow.md)。

| 要修改什么 | 从哪里看 | 模块负责什么 |
| --- | --- | --- |
| 向导、批次、批准文件、历史或报告 | `internal/cli` | 接收操作输入，组织命令和输出 |
| APK 校验和固定保存的发布内容 | `internal/artifact`、`internal/manifest` | 检查 APK、哈希和签名，保存发布快照 |
| 请求派发、状态或崩溃恢复 | `internal/engine`、`internal/state` | 保存 SQLite 操作日志，根据证据计算状态，阻止不安全的继续执行 |
| 渠道接口和查询 | `internal/channels`、`internal/protocol` | 定义各渠道操作、验证规则和能力限制 |
| 账号、凭据或 HTTP | `internal/account`、`internal/credentials`、`internal/transport` | 协调账号操作，读取钥匙串引用，控制请求与上传授权 |
| 模拟渠道和故障验收 | `internal/simulation`、`internal/browser` | 提供本机回环服务、合成浏览器页面和验收测试 |

## 发布路径

按这个顺序检查一次发布如何执行：

1. `setup` 保存项目配置：包名、批准签名、公开账号标识和钥匙串引用名称。
2. `prepare` 检查明确指定的各渠道 APK。包名、版本和签名符合要求后，冻结 APK 与更新说明，创建不可变批次。准备批次时不访问渠道，`setup` 也不访问渠道。
3. `preflight` 读取账号和应用基准，并保存与本次冻结内容的绑定。
4. `batch review` 检查已保存的输入，创建新的不可变批准文件。摘要绑定选定渠道、APK、更新说明、发布规则、配置和已保存的预检。
5. `batch submit` 在派发第一个选定目标前，验证整个已审阅计划。
6. 每项业务请求发出前，先把操作意图记入日志。取得可验证的生效回执后，立即保存回执。

响应丢失时，请求可能已经生效，不能直接重发。`reconcile` 只读核对结果。`resume` 仍需检查原批准和未决写入。同一渠道、账号和应用有较早的未决写入时，新发布也不能绕过检查。

修改派发或恢复逻辑时，要同时检查请求前的持久化、响应验证、回执保存和重启后的读取路径。仅在函数里返回一个错误，不能证明进程崩溃后的行为正确。

## 状态与证据

执行、审核、上架和查询健康状态分别保存。接口受理了提交，只能确认提交已受理。确认审核通过或公开上架，还需要对应证据。观测事实中记录来源、采集时间和争议。未知字段及旧版本证据不能直接确认目标成功。

小米版本比较和应用宝未绑定版本的审核信息保存在 `channel_context` 中。它们不能解决未知写入，也不能增加已核实的审核通过或上架数量。面向操作者的解释见[自动查询说明](channels/automatic-observation.md)。

查询失败时，保留的缓存事实与当前来源健康状态分开记录。失败不会删除有用缓存，也不能让旧数据看起来像刚采集的数据。

## 本地存储与并发

运行目录、日志和钥匙串服务前缀见[本地文件与备份](daily-cli-workflow.md#本地文件与备份)。状态使用 SQLite WAL 和完全同步设置。同一时刻只允许一个本地写入者。账号生命周期协调与应用所有权机制阻止冲突操作。

读取或保存私有文件时，使用现有的私有文件辅助逻辑，保持对路径和权限的检查。命令运行期间不要移动或编辑数据库。

备份保存其实现覆盖的日志状态，以及关联的冻结证据和产物。还原备份后，工具会阻止业务写入，直到完成恢复核对。还原备份不会赋予新的写入授权。操作者的备份范围和步骤见[日常发布](daily-cli-workflow.md#本地文件与备份)。

## 验收边界

测试使用合成账号、凭据、APK、响应、本地 HTTP 服务和浏览器页面。恢复验收会真实终止子进程，再检查日志和重启行为。

这些结果说明实现通过了对应测试，不代表渠道权限、未公开行为或真实账号状态已验证。按变更范围选择检查的规则见[贡献指南](../CONTRIBUTING.md#按变更选择验收)。
