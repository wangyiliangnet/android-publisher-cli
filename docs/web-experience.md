# 本地 Web 用户故事与交互约定

Web 面向熟悉发版业务、低频使用本工具的发布负责人。用户凭应用、商店、版本、安装包等已有经验完成操作。页面先通过结构、命名、默认值和反馈表达含义，必要时再解释字段来源和操作后果。

文案聚焦当前任务、对象状态和下一步操作。问题旁直接放置可执行的入口，例如“重试保存”“打开环境检查”和“核对提交结果”。字段说明用于告知资料来源和填写要求；存储、加密和请求处理过程放在技术文档中。共享账号的影响、提交范围和重试限制在作决定时说明。

## 用户需要理解的概念

界面围绕[领域词汇表](../GLOSSARY.md)中的四个核心概念组织：

| 概念 | 页面中的位置与用途 |
| --- | --- |
| 应用 | 用名称和包名识别要发布的 Android 应用。各商店的应用编号、资料和访问检查结果分别保存。 |
| 商店 | 华为、荣耀、应用宝等发布平台。应用内的商店列表称“发布商店”，本次选中的商店表示提交范围。 |
| 账号 | 操作某个商店的身份，可供多个应用选用。全局入口称“商店账号”，具体商店内简称“账号”。 |
| 凭据 | 证明账号身份的密钥或材料，随账号管理。清除操作称“清除本地凭据”，说明只影响本工具保存的材料。 |

“应用在商店中的登记信息”通过“应用资料”和“商店应用编号”等字段表达，无需增加“商店应用”这一核心对象。账号备注用于本地识别，API 接入标识用于识别账号或客户端。确认页分别列出应用标识、API 接入标识和账号备注，内容来自本次提交计划。

按钮统一使用“填写凭据”“更新凭据”和“清除本地凭据”。更新共享账号或清除凭据时，列出受影响应用。清除后，账号和商店授权仍保留。凭据表单展示账号、关联应用和填写项；文件权限要求仅在选择文件路径时展示。发布批次、冻结副本和协议字段放在折叠详情中。

“移除账号”从本工具的账号列表中移除账号，同时清除本地凭据。仍被应用选用时禁用按钮，列出对应应用的设置入口；有正在执行的提交或未决请求时显示阻止原因。确认时展示商店和账号备注，说明历史发布保留、商店中的真实账号不受影响。历史记录中使用过账号，不等于当前应用仍选用它。

应用名称允许中文，只用于本工具识别应用。命令行短名是稳定标识，供 CLI 选择同一个应用；名称变更不会修改商店中的应用标题。

## 优先用户故事

| 用户故事 | 用户应能直接完成的事 |
| --- | --- |
| 我要发一个新版本 | 找到应用，按商店选包，填写更新说明，检查并确认提交。 |
| 上次发得怎么样了 | 立即看到已有结果、更新时间及各商店提交、审核、上架进度。 |
| 有商店的提交未完成 | 看清提交停在哪一步、已保留内容及下一步，处理后返回原发布记录。 |
| 第一次使用 | 先保存应用，再配置需要的商店和账号；也可以先添加商店账号，无需提供 APK。 |
| 离开后回来 | 找回本地草稿和进行中的操作，复用已完成工作。 |

## 独立管理应用与商店账号

应用、发布商店与账号的操作步骤见[应用配置说明](configuration.md)。

应用和商店账号有独立入口。首页列出应用、商店配置情况和最近发布。只有一个应用时直接进入应用。应用详情以新版本发布、当前草稿、最近发布和发布记录为主。发布商店收为一行名称摘要，通过“管理”进入配置。只有需要用户操作时才展示“接下来要做”；正常的账号访问状态留在设置页。

左侧导航中，“全部应用”是应用列表入口，具体应用缩进为下级快捷入口。“商店账号”和“环境检查”位于账号与设置分组。“商店支持说明”放在内容区页脚，作为产品说明。手机导航保留应用分组，页脚说明仍可访问。

环境检查按“系统兼容性”“安装包检查”和“凭据保存”列出功能状态。安装包检查不可用时，在该项旁直接提供“修复”；正常时只提供“重新检查”。系统不兼容等无法通过安装修复的问题另给处理提示。页面说明聚焦功能状态和下一步操作，版本与运行信息按需展开。

应用详情的“应用设置”包含“基本资料”和“发布商店”两个页签。设置页通过面包屑、应用名称、包名和“返回应用详情”保留当前应用上下文。商店列表用于查看应用编号、选用账号和访问状态，提供“添加商店”和“编辑配置”；移除操作默认折叠。

添加商店按步骤完成，编辑单个商店直接打开该商店表单，完成后可以返回商店列表或应用。表单分为“某商店中的应用资料”和“为此应用选择账号”。全局“商店账号”入口用于管理共享账号、维护凭据和查看关联应用。

创建应用只填写应用名称和 Android 包名，命令行短名放在高级设置中。保存后进入应用主页，可以立即配置商店，也可以稍后处理。尚未配置商店的应用显示“尚未配置商店”，发布前引导配置至少一个商店。

商店账号可以在没有任何应用时添加。创建账号时选择商店，填写账号备注、API 接入标识和凭据。账号页面列出使用它的应用，允许暂未关联任何应用的账号继续独立管理。

配置商店按“选择商店 → 填写应用资料 → 选择账号 → 检查账号访问”展开。页面将填写资料和选择账号合在“应用与账号”一步，分区标题为“某商店中的应用资料”和“为此应用选择账号”。账号访问检查尝试读取应用在该商店中的资料，不表示已确认所有发布权限。已有账号直接复用，也可在当前流程中快捷新增。应用须事先在商店后台创建，工具只保存本地配置。

应用尚未选择商店时，入口称“配置商店”；设置页中的操作称“添加商店”和“编辑配置”。账号管理中的操作称“添加账号”。“发布商店”是应用选定的商店列表；发布流程中的“所选商店”是本次提交范围。

每个商店的配置分别保存应用编号、选用账号和所需资料。商店应用编号、图标和隐私政策属于该应用在该商店的资料；API 接入标识和凭据属于账号。账号备注用于识别账号，不承担应用标识的含义。

凭据状态与应用访问状态分别展示。没有关联应用时，不显示“应用访问已验证”。账号可以访问应用 A，不能据此确认它可以访问应用 B；复用账号后，仍需验证 B 的访问权限。更换账号或商店应用编号后，需要重新检查当前应用在该商店的账号访问。

未关联应用时，凭据只检查格式并加密保存，按钮使用“保存凭据”。已关联应用时分别检查各应用，至少一个应用读取成功后保存凭据；全部失败时保留旧凭据。保存成功只提示“凭据已保存”，各应用分别展示访问检查结果。

未完成的商店配置保存在本地草稿中。首次选择商店由用户明确决定，保存应用和完成商店配置分别反馈。

字段先使用业务名称，如“商店应用编号”，必要时附官方字段名、获取位置和示例。同一对象的称呼在输入、确认、结果和错误中保持一致。已有账号可直接选择，减少重复输入和重复身份。

用以下场景检查对象之间的关系：

| 场景 | 预期结果 |
| --- | --- |
| 先创建“阅读助手”，暂不选择商店 | 应用已保存，尚未配置商店。 |
| “阅读助手”已有华为，需要增加应用宝 | 从“阅读助手”的“应用设置 → 发布商店”添加应用宝，沿用当前应用身份。 |
| 先添加一个华为商店账号，暂不创建应用 | 账号可独立管理，显示暂未关联应用。 |
| 应用 A、B 选择同一个华为账号 | 账号与凭据复用，各自保留商店中的应用资料和访问验证结果。 |
| 应用 A 选择华为和应用宝 | 同一个应用选择两个商店，各自保存应用编号和选用账号。 |
| 华为账号能访问 A，但不能访问 B | 保留 A 的访问结果，B 提示账号访问检查未通过。 |
| 从 A 移除最后一个商店 | A 继续保留，账号和已有发布记录也保留。 |
| 更新或清除 A、B 共用的凭据 | 列出受影响应用，分别反映各应用的访问状态。 |
| 移除未被应用选用、没有正在执行的提交或未决请求的账号 | 账号和本地凭据从可用列表移除，重启后仍保持移除；历史发布身份和回执保留。 |
| 账号被 A、B 选用，或仍有未决令牌申请 | 阻止移除，保留凭据，给出解除应用关联或处理请求的入口。 |
| 清除凭据后再次进入账号页 | 商店账号仍在，显示“待填写”；商店中的账号和授权保持原样。 |
| A 配置华为和应用宝，本次只选华为 | 本次只向华为提交，应用宝的配置仍保留。 |

## 准备、确认和跟踪

1. 准备材料：默认全部已配置商店，按商店明确指定 APK，填写共用更新说明。文件名只用于识别文件。
2. 检查并确认：检查 APK 和商店访问，展示需处理的问题。通过后展示应用、版本、各商店 APK、商店应用编号、账号和说明。
3. 提交与跟踪：用户确认一次后上传和提审。发布方式固定为审核通过后立即上架。

正式提交前可以返回修改 APK、说明和商店，变更后重新检查。已有提交操作的记录保留原内容；需要换材料时准备另一次发布。

保存资料只修改本地配置。保存凭据与检查账号访问分别反馈。提交前检查使用“检查通过”，商店审核结果使用“审核通过”。检查页取消某商店后显示“本次不提交”；全部取消时禁用重新检查，并提示选择商店。

“发布新版本”进入发布草稿。草稿可以保存不完整的材料，也可以在检查通过后继续修改。只有所选商店已有安装包，或更新说明含非空白字符时，才保留发布草稿。只进入页面、选择商店或输入空白不会留下草稿；清空全部材料后移除草稿。每次检查保留当时的材料，修改后重新检查；这些材料检查记录放在折叠详情中，不作为最近一次发布，也不要求逐条提交。查看检查记录时只展示材料，不展示审核、上架或查询结果。

开始提交后进入发布记录，页面标题和返回入口统一称“发布记录”。页面先展示“发布进度”，再展示“各商店发布状态”。“发布结果”只用于描述结论，不能代替包含材料、进度和操作历史的整条记录。“商店结果”不作为页面名称或操作对象。

正式提交按钮说明所选商店及审核通过后的上架方式。普通保存直接完成，正式提交保留一次完整确认。

配置和发布草稿保存到本地私有目录，APK 上传副本在本地服务重启后仍可使用。凭据不进入草稿、浏览器存储或后台操作记录；凭据沿用验证后加密保存的独立流程。

草稿保存失败时，在保存状态旁提供“重试保存”，保留当前输入。更换安装包或说明后，重新检查当前草稿；本次检查失败时，也不能沿用上次材料的检查和提交确认。

表单校验失败后，保留输入和已展开的填写项，便于直接修正。提交请求未返回结果时，引导先查看提交进度，不能据此认定提交尚未开始，也不能直接建议重试。

耗时操作由本地服务执行。页面可以离开，浏览器关闭后服务仍可继续工作。服务中断时，已保存的请求日志和回执是恢复依据。重新进入显示已保存进度，不自动发起新的提交。

## 结果与处理入口

页面先给出结论和待办，再按商店展示依据。例如“4 个商店已提交，1 个商店的提交结果待确认，1 个商店未完成提交”。商店受理本次提交后显示“已提交”，审核通过和公开上架继续分别跟踪。

| 展示项 | 结果与含义 |
| --- | --- |
| 提交 | 尚未提交、正在提交、提交未完成、提交结果待确认或已提交。 |
| 审核 | 暂未确认、审核中、审核通过或审核未通过。提交前检查通过不改变审核状态。 |
| 上架 | 暂未确认、已上架或未上架。商店受理提交不代表已上架。 |
| 查询状态 | 尚未查询、查询成功或本次查询失败，并列出最近成功时间。失败时保留上次结果。 |
| 人工核对记录 | 单列核对结论、核对时间、来源和备注。自动结果保持独立。 |

| 情况 | 页面动作 |
| --- | --- |
| 账号或配置需要修改 | 通过“更新凭据”或“编辑配置”进入对应表单，保存后重新检查。 |
| 确定可以安全重试 | 重新检查并确认本次重试商店，其他商店结果保留。 |
| 提交结果待确认 | 通过“核对提交结果”读取商店回执。仍无法确认时保留记录，请维护者进一步核查，继续阻止重试。 |
| 审核未通过 | 到商店后台查看原因，选择“准备新版本”修改材料。 |
| 商店状态需要人工核对 | 选择“人工核对并记录”，按页面指引核对商店后台的本次版本。 |
| 本次查询失败 | 保留上次结果和时间，提供重新查询。 |

提交结果待确认与人工核对审核或上架是不同待办。人工核对记录不解除缺少关联证据的提交阻塞。不存在可安全执行的提交动作时，不突出“继续”。

上架汇总分别列出自动确认数量和人工核对记录数量。只有全部商店自动确认上架，才显示“本次版本已在全部商店上架”。人工核对为已上架时，支持自动查询的商店继续跟踪；后续自动结果与原人工记录并列展示。本次查询失败时，汇总仍提示失败，已有上架结果保留。

用以下场景核对发布概念：

| 场景 | 页面应表达的含义 |
| --- | --- |
| 已选 APK，更新说明尚未填写 | 发布草稿尚未完成，可以离开后继续。 |
| 材料检查通过后离开，没有确认提交 | 保留发布草稿和材料检查记录；发布记录列表仍为空。 |
| 华为已受理，应用宝的响应丢失 | 一次发布包含两个商店状态：华为已提交，应用宝提交结果待确认。 |
| 全部商店已受理，其中一个仍在审核 | 提交已完成，继续分别跟踪审核和上架，不能概括为“发布成功”。 |
| 商店未返回自动结果，人工核对为已上架 | 保留两个来源的结论，不能把人工记录算作自动确认。 |
| 发布已全部上架，之后查询失败 | 已上架结论保留，同时说明本次查询失败。 |

进入发布记录先展示本地结果，再查询最新状态。页面可见且有待跟踪任务时更新进度；查询失败保留已有结果并标明本次未能更新。进行中的提交展示真实阶段及商店进度。

错误提示说明哪个对象出了什么问题，以及现在能做什么。连接失败时提示检查发布工具是否仍在运行；需要重新加载页面时明确提示刷新。任意后端异常和商店敏感响应不进入普通提示；技术详情按需展开。

## 两端的共同约定

CLI 与 Web 共用应用、账号、发布记录、业务规则和结果含义。Web 使用页面和上下文入口，CLI 使用命令和终端问答。用户可以切换入口查看或继续同一条记录。CLI 沿用现有命令结构，同步名称、结果和处理指引。

## 验收

用合成应用验证首次接入、中文名称、按商店选包、改材料、最终一次确认、部分失败修复和重试、提交结果待确认、人工核对、离开及刷新恢复。检查移动端和键盘操作。

核对以下边界：

- 人工核对为已上架后，仍可获取自动结果。
- 查询失败时，保留已确认结果和上次成功时间。
- 未决请求追加人工核对记录后，仍不能重试。
- 确认页沿用本次提交计划中的账号身份。
- 检查页全部取消商店后，不会启动请求。
- 未提交的材料检查记录不出现在最近一次发布中，也不显示商店结果查询入口。

检查每个主要页面是否能回答：当前处理哪个应用和版本、需要提供什么、点击后会发生什么。主要流程应可凭结构和命名完成；必要解释出现在用户需要作决定的位置。
