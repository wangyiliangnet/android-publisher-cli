# 本地 Web 用户故事与交互约定

Web 面向熟悉发版业务、低频使用本工具的发布负责人。用户凭应用、商店、版本、安装包等已有经验完成操作。页面先通过结构、命名、默认值和反馈表达含义，必要时再解释字段来源和操作后果。

## 用户需要理解的概念

| 概念 | 页面中的含义 |
| --- | --- |
| 应用 | 长期保存的应用资料，以及各商店的接入情况。 |
| 渠道 | 要提交到的商店，包含该商店的应用和发布账号。 |
| 一次发布 | 某个版本的各渠道 APK、共用更新说明及处理进度。 |

发布账号和访问密钥在接入、修复和维护时出现。账号可由多个应用复用，更新或清除时列出受影响应用。API 访问密钥与 APK 签名密钥分别说明。批次、冻结副本、提交计划和协议字段放在技术详情中。

应用名称允许中文，只用于本工具识别应用。命令行短名是稳定标识，供 CLI 选择同一个应用；名称变更不会修改商店中的应用标题。

## 优先用户故事

| 用户故事 | 用户应能直接完成的事 |
| --- | --- |
| 我要发一个新版本 | 找到应用，逐渠道选包，填写更新说明，检查并确认提交。 |
| 上次发得怎么样了 | 立即看到已有结果、更新时间及各渠道提交、审核、上架进度。 |
| 有渠道没完成 | 看清失败对象、已保留内容及下一步，修复后返回原任务。 |
| 第一次使用 | 连续完成应用资料、渠道选择、账号接入和访问验证，无需提供 APK。 |
| 离开后回来 | 找回本机草稿和进行中的操作，复用已完成工作。 |

## 从应用开始

首页列出应用、接入情况、最近发布和当前待办。只有一个应用时直接进入应用。应用内提供新版本发布、发布记录和渠道设置；全局账号及环境检查作为辅助入口。

接入按“应用资料 → 选择渠道 → 逐渠道配置与验证”展开。首次选择渠道由用户明确决定。每个渠道分别显示资料是否保存、凭据是否接入和访问是否验证。尚未完成的输入保存在本机草稿中。

字段先使用业务名称，如“商店应用编号”，必要时附官方字段名、获取位置和示例。同一对象的称呼在输入、确认、结果和错误中保持一致。已有账号可直接选择，减少重复输入和重复身份。

## 准备、确认和跟踪

1. 准备材料：默认全部已配置渠道，逐渠道明确指定 APK，填写共用更新说明。文件名只用于识别文件。
2. 检查并确认：检查 APK 和渠道访问，展示需处理的问题。通过后展示应用、版本、各渠道 APK、商店应用、账号和说明。
3. 提交与跟踪：用户确认一次后上传和提审。发布方式固定为审核通过后立即上架。

正式提交前可以返回修改 APK、说明和渠道，变更后重新检查。已有提交操作的记录保留原内容；需要换材料时准备另一次发布。

保存资料只修改本机配置。验证账号检查访问权限并保存凭据。检查本次发布不提审。正式提交按钮说明所选渠道及审核通过后的上架方式。普通保存直接完成，正式提交保留一次完整确认。

配置和发布草稿保存到本机私有目录，APK 上传副本在本地服务重启后仍可使用。密钥输入不进入草稿、浏览器存储或后台操作记录；凭据沿用验证后加密保存的独立流程。

耗时操作由本地服务执行。页面可以离开，浏览器关闭后服务仍可继续工作。服务中断时，已保存的请求日志和回执是恢复依据。重新进入显示已保存进度，不自动发起新的提交。

## 结果与处理入口

页面先给出结论和待办，再逐渠道展示依据。例如“4 个渠道已提交，1 个提交失败可重试，1 个提交结果待确认”。商店接收提交表示提交完成，审核通过和公开上架继续分别跟踪。

| 情况 | 页面动作 |
| --- | --- |
| 账号或配置需要修复 | 进入对应渠道设置，修复后返回原发布。 |
| 确定可以安全重试 | 重新检查并确认本次重试渠道，其他渠道结果保留。 |
| 提交结果待确认 | 检查原请求结果，解释请求可能已生效，保留重复写入保护。 |
| 商店状态需要人工查看 | 打开对应商店后台，记录本次版本的查看结果。 |
| 本次查询失败 | 保留上次结果和时间，提供重新查询。 |

未决提交与人工查看审核或上架是不同待办。人工记录标明来源和时间，不解除缺少关联证据的提交阻塞。不存在可安全执行的提交动作时，不突出“继续”。

进入发布记录先展示本机结果，再查询最新状态。页面可见且有待跟踪任务时更新进度；查询失败保留已有结果并标明本次未能更新。进行中的提交展示真实阶段及渠道进度。

错误提示说明哪个对象出了什么问题、已完成内容如何保留、现在能做什么。任意后端异常和商店敏感响应不进入普通提示；技术详情按需展开。

## 两端的共同约定

CLI 与 Web 共用应用、账号、发布记录、业务规则和结果含义。Web 使用页面和上下文入口，CLI 使用命令和终端问答。用户可以切换入口查看或继续同一条记录。CLI 沿用现有命令结构，同步名称、结果和处理指引。

## 验收

用合成应用验证首次接入、中文名称、逐渠道选包、改材料、最终一次确认、部分失败修复和重试、未决提交、人工查看、离开及刷新恢复。检查移动端和键盘操作。

检查每个主要页面是否能回答：当前处理哪个应用和版本、需要提供什么、点击后会发生什么。主要流程应可凭结构和命名完成；必要解释出现在用户需要作决定的位置。
