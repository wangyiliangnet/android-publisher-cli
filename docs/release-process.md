# 维护者：版本发布

本流程发布 CLI 的 npm tarball，不会向 Android 商店提交应用，也不会向 npm 注册表发布包。构建与检查命令见[构建与分发](mac-cli-delivery.md)。

## 准备版本

通过 PR 更新 `package.json`、`package-lock.json` 和 [CHANGELOG.md](../CHANGELOG.md)。写明用户可见行为、状态兼容性、已知限制和安装要求。内容变化必须使用新版本号。

等待准确的待发布提交合入 `main`，确认该提交的必需 CI `check` 通过。旧提交上的成功检查不能代替本次检查。随后在本地检出同一提交，按[构建与分发](mac-cli-delivery.md)运行完整检查并生成 tarball 与 `.sha256` 文件。

## 复核草稿

在 GitHub Releases 中为 `vVERSION` 创建草稿，目标指向已检查的 `main` 提交。上传 tarball 和对应摘要文件。草稿说明应列出 Node.js 要求、状态兼容性，以及六个渠道的真实账号验证情况。

从草稿下载两个文件，重新运行 `shasum -a 256 -c`。在隔离的 npm 前缀安装下载的 tarball，检查 `release version --json` 和包内文档。核对标签、提交、文件名和摘要与原检查结果一致，再由维护者手工公开。

创建、上传或复核中断时，先查看 GitHub 上已有的标签、草稿和附件。目标或字节不一致时停止替换，调查后使用新版本号。公开版本发现问题时，发布新版本；不要替换同名附件。

目前仓库不提供自动创建草稿的工作流。PR 检查通过只说明对应测试成功，不代表真实商店账号已验证，也不授权应用提审。
