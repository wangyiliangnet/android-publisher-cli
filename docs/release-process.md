# 维护者：版本发布

按本页创建 CLI 的 GitHub 标签、草稿和公开版本。开始前，按[贡献指南](https://github.com/wangyiliangnet/android-publisher-cli/blob/main/CONTRIBUTING.md)完成 PR、审查和必需 CI。制作团队签名包见[构建与分发](mac-cli-delivery.md)。本流程只发布 CLI 安装包，不向 Android 商店提审。

## 版本规则

工作流输入使用不带 `v` 的 SemVer 风格版本，例如 `0.1.0-beta.1`，生成的标签为 `v0.1.0-beta.1`。开发构建在可用时报告开发版本和提交。

每份不同的安装包都要使用新版本号。不要替换已发布标签，也不要用相同版本号发布不同字节的安装包。

发布前，通过 PR 更新 [CHANGELOG.md](../CHANGELOG.md)，写明用户可见变化、迁移要求、已知限制和分发签名状态。测试版也要说明状态兼容性。

## 创建并复核草稿

### 第 1 步：确认准备发布的提交

确认发布说明和修复已通过正常 PR 合入 `main`。检查准备发布的准确提交，其必需 CI **`check`** 必须通过；其他提交的成功结果不能代替。

### 第 2 步：在 GitHub 启动发布工作流

1. 打开仓库的 **Actions** 页面，选择 **Draft CI Preview**。
2. 点击 **Run workflow**，选择 `main`。
3. 在 `version` 中输入不带 `v` 的版本号，例如 `0.1.0-beta.1`，再启动运行。
4. 等待该次运行完成。失败时查看失败任务，按后面的中断处理操作。

[发布工作流](https://github.com/wangyiliangnet/android-publisher-cli/blob/main/.github/workflows/release.yml)会先核对版本和当前 main，再重新执行完整检查。随后构建 ad-hoc 签名的 arm64 CI 预览，并验收双版本安装、升级、回滚、卸载、篡改和符号链接拒绝行为。

这些检查成功后，工作流才创建轻量标签和 GitHub 发布草稿。它不会自动公开发布。

### 第 3 步：下载草稿中的实际产物

打开仓库的 Releases，找到本次草稿，下载压缩包和配套 `.sha256` 文件。对实际下载的文件完成以下核对：

- 标签和提交与第 1 步确认的提交一致。
- 安装包元数据、校验和、签名、架构和安装结果一致。
- 许可证、第三方声明和使用说明完整。
- 包内文件符合允许清单，没有账号文件、密钥、应用 APK、运行状态、原始响应或私有文档。

安装和包内容的检查步骤见[构建与分发](mac-cli-delivery.md)。

### 第 4 步：审阅说明后公开发布

确认说明明确标注 **CI 预览、ad-hoc 签名、未公证、没有稳定的钥匙串信任身份**。测试版需勾选预发布，再由维护者最终审阅并手工公开。

工作流的任务与权限以配置文件为准。只有草稿任务获得创建标签和草稿所需的写权限，且该任务不检出源码。常规检查不上传发布产物；草稿使用同次运行的不可变产物。正式签名和 Apple 公证另行配置，预览检查通过不代表这些步骤已完成。

## 创建或上传中断

### 先判断能否重跑原任务

若 `main` 仍指向本次已测试提交，在原运行中选择 **Re-run failed jobs（重新运行失败任务）**，保留该次产物字节。不要重新触发或构建来替换已有匹配草稿，因为新构建可能生成不同字节。

重跑时，工作流会核对轻量标签、草稿元数据和预期摘要，再下载已有资产校验字节。核对一致后，只上传缺失文件。

### 遇到冲突时停止替换

已公开版本、标签目标不同、元数据或字节冲突、额外资产，都会使工作流拒绝继续。它不会替换标签或已有资产。若 main 已变化或冲突仍在，先调查，再按正常流程准备新版本。

候选验收失败时，通过 PR 修复后构建新候选。公开发布后发现问题，也应提供新版本。工具回滚只切换本机程序，不撤销商店写入，也不绕过本地状态结构检查。
